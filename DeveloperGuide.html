TuitionBook Developer Guide

This guide is for developers maintaining TuitionBook and testers checking its behaviour. It explains the component boundaries, implemented features, scope decisions and manual test scenarios. It assumes familiarity with Java, object-oriented programming and basic UML diagrams. For everyday contact-management tasks, use the User Guide.

Reading paths:

  • New contributor: start with Setting up, then read Architecture and the relevant Implementation section.
  • Feature or bug investigation: check Product scope, the relevant command in the UG, and Scope decisions before tracing parser, command, model and storage behaviour.
  • Tester: use Testing for automated checks and Manual testing for copyable scenarios and expected results.

Version: This guide describes the unreleased development source for v1.5. Its command-input changes, strict prefix checks and quoted addresses are not in the published v1.4 JAR. Requirements state intended guarantees, not measured test results. Historical proposals and deferred work are labelled separately from implemented behaviour. Consult the release history for published versions.

TuitionBook is scoped to English-language users and any en-* locale (for example, en-SG, en-GB, or en-US). Text input is encoded as UTF-8. Field-specific validation rules apply to names, addresses, phone numbers, email addresses, and tags.

Design

Architecture

The architecture diagram above shows the main components. The following sections explain their responsibilities and the direction of calls between them.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, PersonListPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

CommandBox uses CommandTextField, a TextField subclass that converts pasted tabs and line separators to spaces before JavaFX filters them. This preserves word boundaries while keeping each command on one line. Pasted text is inserted into the field but is not executed until the user presses Enter.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Person objects from the model.

PersonListPanel receives both the filtered contact list and the complete contact list from Logic. It displays the filtered list while using the complete list to resolve a student's guardian name and contact number and a guardian's linked student names, including when a role filter hides the related contacts' cards. The panel refreshes its cards when the complete list changes so that relationship details remain current.

How the Logic component works:

  1. When Logic is called upon to execute a command, the command is passed to a TuitionBookParser object, which creates a parser that matches the command (e.g., DeleteCommandParser) and uses it to parse the arguments. It creates HelpCommand, ExitCommand, and ReloadCommand directly instead.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteCommand) which is executed by the LogicManager.
  3. Before executing a command that can mutate contacts, LogicManager copies the contact data and retains the active filter for rollback. It calls execute(model, storage); for DeleteCommand, the inherited method delegates to execute(model). The inherited delegation is omitted from the second diagram.
  4. DeleteCommand resolves the displayed index against the filtered list, identifies affected students from the complete contact list, and passes the resolved Person to Model.deletePerson. Deleting a guardian clears the affected students' guardian links. The second diagram omits the complete-list lookup and model-internal link updates, which do not change the main command flow.
  5. Each Command declares whether it requires contact data to be saved. After a command executes successfully, LogicManager saves the Model's contact data only when the command requires it. The second diagram shows the successful save path. If saving throws an IOException or AccessDeniedException, LogicManager restores the contacts and active filter that existed before the command, then throws a CommandException; those rollback calls are deliberately omitted from the diagram.
  6. The result of the command execution is encapsulated as a CommandResult object which is returned from Logic.

How the parsing works:

  • TuitionBookParser creates a command-specific parser for add, edit, tag, untag, delete, clear, find, list, link, unlink, and view. Each implements Parser<T extends Command> for its command type. The diagram shows AddCommandParser and TagCommandParser as representative examples; the remaining command-specific parsers are omitted.
  • AddCommandParser uses ArgumentTokenizer, ArgumentMultimap, the Prefix constants in CliSyntax, and ParserUtil to parse arguments and construct an AddCommand. EditCommandParser, ListCommandParser, and ViewCommandParser also use these utilities. Other parsers use only the helpers they need; for example, DeleteCommandParser, LinkCommandParser, and UnlinkCommandParser use ParserUtil to parse indexes.
  • TagCommandParser and UntagCommandParser delegate argument parsing to the package-private TagModificationCommandParser helper, passing their respective command constructor references. The helper uses the same tokenization and validation utilities and invokes the supplied constructor after parsing. It does not implement Parser.
  • ArgumentTokenizer creates an ArgumentMultimap, which stores argument values keyed by Prefix. CliSyntax defines the recognized prefix constants; ParserUtil parses values and indexes without depending on Prefix.
  • TuitionBookParser creates HelpCommand, ExitCommand, and ReloadCommand directly, without a command-specific parser, after rejecting non-blank arguments. In all cases it returns the resulting object as a Command.

Command-input boundary

CommandTextField converts pasted tabs and line separators to normal spaces before the text reaches the parser, including inside quoted values. A CRLF pair becomes one space. This GUI conversion preserves word boundaries and does not execute the pasted text.

As a fallback for raw input that reaches it without command-box conversion, TuitionBookParser rejects actual line breaks before trimming or dispatching, using Java's \R definition (CR/LF, vertical tab, form feed, NEL, line separator and paragraph separator). The error identifies the first line-break code point. This also applies inside quotes and at the input edges; the parser does not split or join multiple commands. Normal GUI paste therefore does not produce this line-break diagnostic.

Only the extracted command word is lowercased with Locale.ROOT. Prefixes, arguments, quoted values, tag identity and the exact confirm keyword are not case-normalised. This keeps command lookup independent of the computer's locale without changing contact data.

ParserUtil.checkForUnsupportedSpaces diagnoses NBSP (U+00A0) and ideographic/full-width space (U+3000) only in command words, no-argument command tails and positional-index text. It does not scan field values. Indexed command parsers perform this check before wrapping ordinary invalid-index errors in command-specific usage, and link checks before splitting its two indexes. parseIndex also checks direct callers. Other invisible-character policies and field validation remain outside this change.

These failures occur during parsing, before command execution, model mutation or contact saving. help, exit and reload with extra arguments never produce an executable command. See Command input and diagnostics for manual scenarios.

Model component

API : Model.java

The Model component,

  • stores TuitionBook data i.e., all Person objects (which are contained in a UniquePersonList object).
  • stores the Person objects selected by the current filter, such as search results, in a separate filtered list. It exposes this list as an unmodifiable ObservableList<Person> that the UI can observe and bind to, so the UI updates when the list changes.
  • stores a UserPrefs object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Note: The alternative, arguably more object-oriented, design below keeps a unique list of tags in TuitionBook, and each Person references tags from that list. This lets TuitionBook maintain one Tag object per unique tag instead of each Person holding its own Tag objects.

Storage component

API : Storage.java

The Storage component,

  • can save both TuitionBook data and user preference data in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonTuitionBookStorage and JsonUserPrefsStorage (one class per data file).
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)

JsonUtil removes an optional UTF-8 BOM and decodes file bytes with a strict UTF-8 decoder before passing the text to Jackson, while retaining the same string-based parsing for in-memory callers. Invalid UTF-8 and other encoded files are therefore rejected instead of being accepted with replacement characters or silently converted on the next save. The shared mapper also requires the input to end after one JSON value and rejects duplicate property names at any object depth. These checks prevent malformed, trailing, or conflicting content from being accepted and then discarded by a later save. For the configured contact file, parsing failure enters the existing malformed-file recovery path, which moves the original bytes unchanged to an unused sibling backup or blocks saving when that backup cannot be created.

DataLoadingException walks its cause chain to produce bounded user guidance for permission denial, invalid contact values, invalid UTF-8 or JSON, and other file-system failures. It does not expose exception types, paths from the cause, or stack traces. MainApp carries this guidance through StartupNotice; UiManager combines it with the actual backup outcome. ReloadCommand uses the same guidance while retaining the current contacts and filter after a failed read.

ApplicationPaths resolves application-managed files before file logging starts. Packaged execution uses the directory containing the executable JAR as the application home, independent of the process working directory. Development runs from compiled class directories use the process working directory as an explicit fallback. Contact data, legacy data migration, preferences, logs, and log rotation/lock files therefore share the same application home.

At startup, MainApp uses tuitionbook.json when it exists. Otherwise, it attempts to move the legacy addressbook.json to that current path. A failed move is logged without aborting initialization: the unchanged legacy path is passed to storage for that run, and migration is retried on a later launch. This preserves readable contacts when directory permissions prevent renaming. If the same permissions also prevent saving, the normal command save-failure rollback restores contacts and the active filter.

Implementation

This section describes some noteworthy details on how certain features are implemented.

Incremental tag changes

tag INDEX t/TAG [t/TAG]... adds tags by set union; untag INDEX t/TAG [t/TAG]... removes them by set difference. add continues to accept an initial tag set and edit continues to replace the whole set. Stored tag identity is case-sensitive, unlike the case-insensitive list filter. Duplicate arguments are deduplicated, existing tags are ignored on addition, and absent tags are ignored on removal.

TagCommandParser and UntagCommandParser delegate index and tag validation to TagModificationCommandParser. It uses ArgumentTokenizer.tokenizeWithQuotedValues with only PREFIX_TAG, protecting embedded prefix-like text inside quoted tags and decoding the same quote and backslash escapes as add, edit and list. Unsupported field-like prefixes outside quotes are rejected rather than absorbed into tags. Every decoded tag is validated before constructing a command, so malformed quotes and invalid or blank tags reject the entire operation. See Quoted field parsing for the shared quoting rules.

TagCommand and UntagCommand share execution through TagModificationCommand. It resolves the displayed index and modifies a disposable copy of the selected contact's tags. A changed set produces one replacement Person retaining its ID, role, relationship, and all other fields, then restores the full list. A no-change result preserves the filter and requests no save. canMutate() remains true before execution so LogicManager captures the rollback snapshot, while requiresSave() is reset each execution and becomes true only after an actual tag change. Existing storage and save-failure rollback apply without a schema change.

TagCommand compares requested tags with the original contact's tag set to report only newly added tags in its success message. UntagCommand uses the same comparison to report every absent tag, both when other tags are removed and when nothing changes. Shared feedback formatting sorts names and encloses them in double quotes, escaping literal quotes and backslashes for unambiguous display. This formatting does not change tag matching or command parsing. The difference is recomputed on each execution rather than retained as command state.

Viewing contact relationships

ViewCommandParser parses view INDEX [v/] with the same positive-index rule as other index-based commands. The optional empty v/ prefix selects full details for linked contacts; the parser rejects duplicate prefixes and values after v/.

ViewCommand selects the contact from Model#getFilteredPersonList(), then reads the full TuitionBook to resolve relationships by persistent contact ID. Thus, a filtered list determines the selected index but cannot hide a linked guardian or student from the result. The command does not change the model or its active filter.

Without v/, the command displays each linked contact as NAME (CONTACT_NUMBER): the linked guardian for a student or linked students in contact-list order for a guardian. With v/, it displays each linked contact's full details. It displays No guardian linked. or No students linked. when the selected contact has no relationship. Missing optional fields use -, and tags are sorted alphabetically.

ViewCommand returns a CommandResult containing a short feedback message and the formatted detail text. MainWindow shows that text in DetailDisplay, which replaces PersonListPanel in the main content area. Executing a command that has no detail text, including an invalid command, restores PersonListPanel. The list and its active filter remain in the model while the detail view is visible.

Contact field validation

Name, Phone, Email, and Address are model value objects that enforce their constraints at construction. Command parsers trim surrounding input whitespace before constructing these objects, but do not otherwise normalize or truncate accepted values. Names support Unicode letters, numbers and combining marks plus ordinary ASCII spaces (U+0020) and the documented punctuation, including straight and right curly apostrophes, and contain at most 100 Unicode code points. Other Unicode whitespace is not valid inside a name. Phone validation uses a linear parser shared with identity normalization. It accepts an optional leading +; plain or parenthesized digit groups separated by one or more ASCII spaces, one hyphen, or one slash; at most one trailing parenthesized annotation; and an optional numeric x, ext, or ext. extension. An annotation is separated from the main number by at least one ASCII space, contains at least one ASCII letter, and otherwise contains only ASCII letters, digits, and single internal spaces. The parser rejects malformed or nested parentheses, empty groups, doubled or trailing punctuation separators, malformed annotations, unsupported letters, and malformed or repeated extensions. Email validation implements the documented ASCII local-part and domain-label subset, including apostrophes and internal consecutive hyphens used by punycode labels, while rejecting consecutive periods.

Addresses contain at most 200 Unicode code points and must contain at least one meaningful visible code point. Address excludes code points for which Character.isWhitespace or Character.isSpaceChar is true, and code points in the Unicode control (Cc) or format (Cf) categories, when deciding whether content is nonblank. These excluded code points may coexist with visible text, so legitimate combining marks or formatting characters do not make an otherwise visible address invalid. LF, vertical tab, form feed, CR, NEL, line separator and paragraph separator characters are always rejected so every stored address is single-line.

NameComparisonUtil#toUnicodeComparisonForm centralizes the locale-independent transformation used for Unicode name comparison: NFC normalization, lowercase with Locale.ROOT, uppercase with Locale.ROOT, then NFC normalization again. Lowercasing before uppercasing makes both Groß and GROẞ become GROSS; it also makes Straße and STRASSE equal and preserves canonical equivalence between composed and decomposed accents. This standard-library sequence is not complete Unicode case folding and does not promise that every linguistically equivalent spelling compares equally.

Duplicate identity and search apply that shared low-level form differently. Person#normalizeNameForIdentity first trims surrounding ASCII spaces and collapses consecutive internal ASCII spaces, then applies the Unicode comparison form; the normalized phone must also match. NameContainsKeywordsPredicate applies only the Unicode comparison form to the stored name and every original keyword before literal substring matching. Search neither trims nor collapses the stored name and does not call the complete identity normalizer. Both paths preserve the original name for display and storage.

Phone identity removes ASCII spaces, hyphens, slashes, and numeric-group parentheses, ignores the annotation, retains a leading +, and converts each supported extension marker to x while retaining its digits. Contacts are duplicates only when both their normalized names and normalized phone numbers match.

JsonAdaptedPerson uses the same model validators when loading JSON, keeping add, edit, and storage validation consistent. An address remains optional, and edit INDEX a/ stores no address rather than an empty Address. A data file containing an over-limit, whitespace-, control-, or format-only, or multi-line address is rejected through the invalid-data recovery path. If the configured file can be moved to an unused sibling backup, the backup preserves the original bytes and saving new data is allowed. If that backup move fails, the original file remains in place and saving stays blocked until a successful read.

After tokenization and duplicate-prefix checks, AddCommandParser collects absent mandatory prefixes in the fixed order r/ROLE, n/NAME, p/PHONE. A structurally valid command with any absent prefixes reports all of them followed by AddCommand.MESSAGE_USAGE; malformed preambles and tokenizer failures retain their existing format or parsing errors. Empty supplied values remain field-validation errors, so the parser does not duplicate model validation.

PersonListCard.fxml gives the role badge its preferred minimum width while allowing the name label to shrink. Each student card has one relationship row for its guardian's name and contact number, and each guardian card uses the same row for linked student names in contact-list order. Long names, phone numbers, email addresses, relationship summaries, addresses, and tags retain their beginning and use an ellipsis within the card instead of widening it or pushing the badge out. PersonCard attaches a wrapped tooltip containing each full value; view INDEX v/ also provides the full relationship details through the keyboard-driven workflow. Multiple tags continue to flow in alphabetical order.

Quoted field parsing

AddCommandParser and EditCommandParser opt into ArgumentTokenizer.tokenizeWithQuotedValues for PREFIX_NAME, PREFIX_ADDRESS and PREFIX_TAG; ListCommandParser and the shared TagModificationCommandParser for tag and untag opt in for PREFIX_TAG. The tokenizer automatically recognises those quoted prefixes, visits candidate positions in order and ignores positions inside a quoted value. It then removes the enclosing quotes before normal field validation. It rejects unclosed quotes and trailing text outside the closing quote. Other fields retain their existing quote behaviour. The model and JSON store decoded values, so no storage migration is needed.

For these five field-based commands, a prefix-like token is one or more ASCII letters followed immediately by /, at the start of the argument string or after an ordinary ASCII space (U+0020). Such a token outside a supported quoted value must match a prefix recognised by that command, including case. Unknown candidates join the same position-ordered scan as known prefixes, so quoted content is skipped before an unknown-prefix error can be raised. The error identifies the token and offers either correcting the command syntax or quoting the complete literal name, address or tag. It does not guess which field was intended.

This deliberately changes some unquoted commands: n/Muhammad s/o Ali and t/Advanced Math/Science now need complete-value quotes. Non-boundary slashes such as t/Math/Science and URL punctuation such as https:// are not new field boundaries. Recognised unquoted prefixes still start separate fields; the parser cannot detect every accidental use of an otherwise supported prefix. The older tokenize method retains its existing contract for other callers.

Inside quoted values, \" decodes to a literal double quote and \\ to a literal backslash. Other backslash sequences and all unquoted values are preserved. The closing-quote scan and decoding use the same escape predicate, so an escaped quote cannot end a value or expose embedded prefixes. An escaped final quote without a subsequent closing quote is rejected. Surrounding whitespace is trimmed as before, and decoded values pass through the existing domain validators; escaping does not widen name validation.

Literal quotes already present in JSON are retained: CLI escaping is decoded before storage and does not change the JSON format or reinterpret stored strings. For example, a stored tag "Sec 4" can be filtered using list t/"\"Sec 4\"", and a/"\"Block A\"" enters an address with literal quotes around it. Existing addresses and tags are not stripped or normalised on loading. Surrounding whitespace continues to be trimmed even inside quoted values; this change does not resolve the padded-JSON-tag issue #185 or change tag case identity.

Appendix: Requirements

Product scope

Target user profile:

  • is a private one-to-one tutor who travels to students' homes
  • manages a significant number of students and guardians
  • needs to maintain student and guardian contact information and their relationships in one place
  • needs to retrieve the relevant guardian's contact details and home-address information quickly
  • benefits from grouping contacts by academic level, subject, tags, or area
  • prefers a single-user desktop application
  • can type quickly, prefers typing over other input methods, and is comfortable with a command-based interface
  • prefers contact information to be stored locally and restored automatically between application sessions
  • uses English and an en-* operating-system locale

Value proposition: TuitionBook is designed to help private one-to-one home tutors manage student and guardian contacts, organise contacts with roles and tags, and retrieve the correct contact details quickly, instead of using a generic contact list or manually cross-referencing separate records. Guardian links and home addresses are optional. Tutors can label academic levels and subjects using generic tags, for example t/Sec4 t/AMath when adding or editing a contact. Dedicated level/subject fields and filtering by those fields are descoped from the final release; they remain possible future enhancements, not promised features. Level and subject grouping is supported through list r/student t/Sec4 t/AMath, which requires both tags. See the tag workflow.

TuitionBook is intended for English-language users and supports en-* operating-system locales. Its interface, documentation, and messages are in English; this does not require contact information to contain only English text. Contact fields accept UTF-8 text subject to their documented validation rules. In particular, names accept Unicode letters, numbers, and combining marks plus ordinary ASCII spaces (U+0020), with the accepted capitalization, punctuation, and Unicode representation preserved after surrounding command-input whitespace is trimmed. Duplicate-contact checks apply the documented locale-independent Unicode comparison form after identity-specific ASCII-space normalization; this covers canonically equivalent accents and the demonstrated sharp-S cases without claiming complete Unicode case folding. See the User Guide.

TuitionBook focuses on contact and relationship management; lesson scheduling, attendance, fees, academic-progress tracking, and messaging are outside its scope.

Decision 4.1: Undo and confirmation

US20 undo/redo is excluded from the final release. There is no command history that can restore a successful deletion or clear operation; users should back up the data file before bulk changes. General confirmation prompts are also excluded. The later #141 decision adds a specific safeguard: clear confirm is required, and the message explicitly includes contacts hidden by filters. delete INDEX remains immediate. Save-failure rollback is implemented and restores contacts and the active filter after a failed save; it is distinct from user-invoked undo and does not reverse a successful command.

Help and notes

The earlier US12 descope was reversed by #93: Help now includes an offline command summary, with browser access to the full UG and Copy URL as a fallback. It is a static syntax summary, not a context-sensitive help system.

US29 free-text notes remain excluded. Notes would need a deliberate syntax for text containing field-like prefixes; simply introducing another prefixed field could interpret part of a note as another argument. Name quoting under #97 was extended to tags by #163. The v1.5 development source also supports quoted addresses alongside strict unknown-prefix checks for #193/#201. Quoted names, addresses and tags support \" for a literal double quote and \\ for a literal backslash, subject to field validation. This protects embedded prefixes in those quoted fields; it does not add notes or quoting for every field. See Quoted field parsing.

Academic grouping and inactive contacts

US18/US19 needs are supported through generic tags: t/Sec4 t/AMath records a level and subject, and list r/student t/Sec4 t/AMath selects students with both labels. Dedicated academic fields and validation remain excluded. This updates the value proposition clarified in #131.

Active and Inactive are ordinary organisational tags. They do not hide contacts, archive records, disable commands, or change guardian relationships. Tutors explicitly select list r/student t/Active when needed. Editing tags replaces the full set, so an edit changing status must retain every other desired tag, for example edit 1 t/Inactive t/Sec4 t/AMath. The later #164 decision, implemented in #166, adds tag and untag for incremental changes without retyping unrelated tags. These commands match stored tags case-sensitively and do not enforce mutually exclusive status labels. Dedicated archive/restore functionality remains excluded from the final release.

Tag identity and compatibility

#155, implemented in #160, deliberately broadens #152's single-hyphen rule to allow natural spaced labels and printable ASCII punctuation. Parsing trims surrounding whitespace, including inside quoted values, while internal spaces remain significant (Sec 4 and Sec 4 differ). Stored tag identity is case-sensitive; filtering compares complete tags case-insensitively. Under #163, enclosing quotes delimit a value and are not stored; inside quoted values, \" decodes to a literal double quote and \\ to a literal backslash. Recognised unquoted prefixes still start fields; the v1.5 development build rejects unsupported space-separated letter prefixes. Quoting the complete tag protects embedded prefixes in add, edit, list, tag and untag; see the UG for examples.

Tag length is deliberately unbounded. The validator uses a linear scan, and cards truncate long values with an ellipsis while retaining the full text in a tooltip and detail view. This is not a guarantee of unlimited resource capacity. Once broader tags are saved, narrowing validation or normalising existing tag identities requires an explicit compatibility or migration plan.

Single-instance operation and manual file editing

Run only one TuitionBook instance against a data file. The application does not lock the file against another instance or an external editor; each save writes the current in-memory contacts and can overwrite another writer's changes. Atomic saving protects replacement of an individual file, not coordination between independent writers.

A lock-file guard was considered and deferred from v1.x because cross-platform locking and stale-lock recovery add risks in the final iteration. The supported manual-editing workflow is to close TuitionBook, back up and edit the file, then reopen it. The implemented reload command remains an explicit recovery option: it replaces in-memory contacts rather than merging concurrent changes. Single-instance enforcement is a deferred improvement, not an implemented safeguard or promised release feature.

Startup and unnecessary writes

US47's Week-5 sample-data status is superseded by #109: a missing data file starts with an empty contact list, and a valid file containing an empty contact list stays empty. The application does not insert sample contacts on startup.

#165 resolves unnecessary save attempts for repeated links, unchanged edits and clearing an empty contact list. Together with unlink and the incremental tag commands, contact-changing commands report their actual mutation through requiresSave(). Commands that leave contact data unchanged do not attempt a save; filter changes alone do not require saving. An unchanged edit still restores the full list, while an unchanged link, unlink, tag or untag preserves the filter. Rollback snapshots remain in place for commands that can mutate data, and actual changes retain normal save-failure rollback. Snapshot creation still copies O(n) contact references; no constant-time execution or measured speedup is claimed. See Saving data for the contract and manual checks.

Role-filter command rule

The filtered form supersedes the plain-list rule: list displays all contacts and clears any active filter, while list r/ROLE and list t/TAG... display contacts matching the supplied criteria. Role matching and tag matching is exact and case-insensitive, and all supplied tags must be present. Other trailing text is rejected.

Startup data rule

If the configured data file is missing, TuitionBook starts with an empty contact list instead of creating sample contacts. An existing valid data file containing no contacts also remains empty after restart. This rule does not change the separate recovery behaviour for a malformed data file.

Malformed-file recovery policy

When the configured data file cannot be read, TuitionBook tries to move it unchanged to a sibling backup named <data-file>.backup. If that name is occupied, it tries <data-file>.backup.1, then increasing numeric suffixes. After a successful move, the load failure carries the exact backup path and bounded cause-specific guidance to the UI. TuitionBook starts with an empty contact list, can save new data at the configured path, and shows appropriate permission, encoding/JSON, contact-value, or file-system recovery steps in both a warning dialog and the result display. If no backup can be created, it leaves the original file in place, blocks saving so that it cannot be overwritten, and presents the same cause-specific guidance before asking the user to reload or restart.

Non-Functional Requirements

  1. TuitionBook shall run without an application installer on any mainstream desktop operating system with Java 25 or later installed.
  2. TuitionBook shall support at least 1,000 contacts. On a reference workstation with a dual-core 1.6 GHz processor, 8 GB RAM, and Java 25, each listing, finding, filtering, viewing, adding, editing, deleting, tagging, untagging, linking, or unlinking command shall complete within two seconds for a data set of 1,000 contacts, measured from command submission to the result being displayed.
  3. All documented add, edit, delete, list, find, filter, view, tag, untag, link, and unlink operations shall be executable through keyboard-entered commands, without requiring a mouse.
  4. TuitionBook shall operate as a single-user desktop application and shall not require a network connection for its normal contact-management functions.
  5. TuitionBook shall store contact data only in a local, human-editable text file and shall not transmit contact data to an external service.
  6. Changes made by successful mutating operations shall be available after a normal application restart. If saving a mutating operation reports a storage error, TuitionBook shall restore the contacts and active filter to their state before that operation.
  7. TuitionBook shall recover without terminating unexpectedly when its local data file cannot be loaded cleanly: if the file is missing, it shall start with an empty contact list and show an information dialog; if it is malformed and a backup succeeds, it shall retain a backup of the malformed file, start with an empty data set, show the exact backup path and recovery steps in a warning and result display, and allow saving; if that backup fails, it shall retain the original file, start with an empty data set, show that saving is blocked and how to remedy it, and block saving; if it contains an invalid guardian link, it shall load the valid contacts, omit the invalid link, and show a warning.

Glossary

  • Contact: A record in TuitionBook representing either a student or a guardian, with a name, phone number, and optional email address, home address, and tags.
  • Current contact list: The contacts currently displayed after applying any active filter; indexes in index-based commands refer to this list.
  • Contact ID: A unique, persistent identifier assigned by TuitionBook to a contact.
  • Data file: The local text file that stores TuitionBook contacts and their recorded guardian links between application sessions.
  • Filter: A condition that restricts the current contact list. TuitionBook supports a name filter or a combined role-and-tag filter; applying a new filter replaces the previous one. The role is optional, and all supplied tags must match exactly, ignoring case.
  • Guardian: A contact with the guardian role. A guardian contact may have zero or more recorded student links; these links record information in TuitionBook and do not establish or determine real-world responsibility.
  • Guardian link: A recorded association from a student to a guardian contact. A student has at most one guardian link, while a guardian can be linked to multiple students.
  • Home address: A stored lesson or contact address, usually associated with a student; it can include details such as a unit number, gate code, or lift instructions.
  • Index: A positive one-based position in the current contact list, used by index-based commands.
  • Mainstream OS: Windows, macOS, or a commonly used Linux distribution.
  • Normalised name: A UTF-8 name converted to its duplicate-identity form: leading and trailing ASCII spaces are removed, each internal run of ASCII spaces is collapsed to one, and the shared Unicode comparison form is applied while the original display value remains unchanged. Search uses only the Unicode comparison form, without this space normalization.
  • Normalised phone number: A phone number converted to its comparison form before duplicate checking: ASCII spaces, hyphens, slashes, and numeric-group parentheses are removed; the optional annotation is ignored; a leading + is retained; and x, ext, and ext. become x while retaining the extension digits. Country-code equivalence is not applied in the MVP.
  • Private tutor: A tutor who provides one-to-one tuition and travels to students' homes.
  • Role: A contact classification. Users may enter student or guardian in any casing; TuitionBook stores and displays the corresponding STUDENT or GUARDIAN role.
  • Student: A contact with the student role who may be linked to one guardian.
  • Tag: An optional user-defined label attached to a contact for categorisation or filtering. Its name is non-blank printable ASCII (U+0020 to U+007E), including spaces and punctuation. Tag validates with a linear scan, without a length limit or recursive regular expression. Command parsing trims surrounding whitespace; internal spacing and spelling are preserved. Optional enclosing quotes protect recognised command prefixes and are removed before validation. JSON retains the plain tag string without migration. Tag.equals and hashCode remain case-sensitive; only list filtering uses exact case-insensitive comparison, requiring every requested tag and the optional role to match. find remains name-only.

Saving data

LogicManager uses canMutate() to snapshot contacts and the active filter before commands that can change data. After successful execution, it saves only when requiresSave() returns true; it does not compare the complete contact list. Each contact-changing command starts with a false save decision, resets it at the start of every execution, and sets it only after changing contact data. These commands override canMutate() to remain true independently of their latest save decision. Reusing a command after an earlier change therefore cannot cause a stale save request on a later no-change or rejected execution. Read-only commands and reload always return false from requiresSave().

link requests saving only after creating or replacing a relationship; unlink only after removing one. edit compares the selected contact's stored values with its proposed replacement and requests saving only when they differ; the replacement preserves the persistent ID. An unchanged edit still restores the full displayed list, as documented in the UG. clear checks whether the complete book contains any contacts, including hidden contacts. Successful additions and deletions always request saving. Filter changes alone do not trigger saving. Actual changes retain the existing save-failure rollback.

Performance: The save decision no longer scans all contacts: it uses the command's mutation outcome, an emptiness check for clear, or a comparison of the selected contact for edit. Comparing that contact's fields and tags still depends on their sizes. Creating the rollback snapshot still copies O(n) contact references; this change does not make overall command execution constant-time. No benchmark has established a user-visible speedup.

A failed load whose backup also fails does set the write block: correct or move the file and use reload (or restart) before retrying contact-changing commands. If backing up an unreadable file succeeds, saving is already enabled and no reload is required. Reload reads the file; it does not save or replay a failed command.
